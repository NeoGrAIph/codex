# Agent role templates

## Feature passport

- Code name: `agent-role-templates`
- Status: native TUI-итерация расширена для `fork/140`; markdown/persona runtime loader не добавлен, но `/agent-roles` теперь даёт inline editor для existing user TOML roles, staged create/update actions, catalog-backed model/provider/reasoning picker controls, вход в existing `/import` flow, а external-agent migration компилирует OpenClaude-style markdown/frontmatter agents, including `tools`/`disallowedTools`, в native `$CODEX_HOME/agents/*.toml` `[tool_selection]`.
- Goal: дать sub-agents осмысленные роли и инструкции через native role templates, чтобы пользователь мог видеть, создавать, проверять и применять специализации без ручного повторения роли в каждом prompt.
- Scope in: native TOML role catalog, built-in/configured role projection, parser-validated TOML draft wizard, inline editor for existing `$CODEX_HOME/agents/*.toml` user roles, TUI list/detail/create/open-file/import-entry flow, catalog-backed model/provider/reasoning default authoring, source/provenance states, current-session runtime in-use evidence, spawn-agent role selection through existing `agent_type`.
- Scope out: markdown role runtime loader, persona manifest, persistent color/memory metadata without native source of truth, standalone role-template app-server write protocol; runtime limits и cwd описываются отдельно. Role tool-selection runtime enforcement and external whole-policy write API are documented in `agent-role-tool-selection`, while this feature owns the `/agent-roles` TOML draft/editor controls that can author `[tool_selection] allowed_tools` / `denied_tools`.

## Как работает для пользователя

Пользователь открывает `/agent-roles` или `/agents`, видит built-in и user templates, создаёт новый user template через предзаполненный native TOML draft, редактирует существующий user TOML прямо в inline editor или через staged actions для current model/current reasoning/current tools, выбирает model/provider/reasoning defaults из native model catalog, импортирует markdown/frontmatter agents через existing `/import`, и затем просит Codex запустить sub-agent с `agent_type` равным имени роли. Built-in роли остаются read-only в wizard: для настройки нужно создать отдельную user role или вручную добавить same-name native TOML/config, который штатный loader покажет как shadowing.

## OpenClaude-inspired target

OpenClaude `AgentsMenu`, `AgentDetail`, `AgentEditor`, `CreateAgentWizard` and `ToolSelector` используются как UX reference, но не как формат данных. Codex role templates должны оставаться TOML-native:

- source of truth: `Config.agent_roles` plus built-ins, not a separate profile registry;
- persistence: `$CODEX_HOME/agents/*.toml` and existing `ConfigToml` parser path;
- binding: `spawn_agent.agent_type`, `apply_role_to_config`, `resolve_role_config`;
- authoring: wizard opens a native TOML draft with `name`, `description`, `nickname_candidates`, `developer_instructions` and a commented `[tool_selection] allowed_tools` hint; existing user roles expose an inline native TOML editor that reads the current `$CODEX_HOME/agents/<role>.toml` file as text, validates it with the existing role parser and writes through the same update/reload path; current-model/current-model-provider/current-reasoning/current-tool staged actions seed the same editable TOML draft, catalog-backed model/provider/reasoning picker controls write selected `ModelPreset` defaults into that draft without switching the current session model, and discovered user roles can set/clear native model defaults, update only model/provider defaults, update only reasoning/service-tier defaults, plus edit `[tool_selection] allowed_tools` / `denied_tools` through staged actions; submitted draft must pass existing role-file parser validation before writing `$CODEX_HOME/agents/<role>.toml`;
- source states/detail: basic `user active`, `built-in active` and `built-in shadowed` are implemented from native role provenance; selected detail shows source, status, config file, config origin, editable native TOML fields, parser validation status for user role files, declaration-field summary, declaration config-layer origins where available, TOML field summary, bounded field-source provenance, loader-derived inherited/overridden role metadata provenance, file-level selected `config_file` detail for effective runtime TOML fields where available, nicknames, current-session runtime in-use summary, role locks, declared tool-selection allowlist/denylist, current-thread runtime catalog reference when available, runtime binding and current-session availability boundary. Richer effective/configured/editable/partial/ignored/disabled/new-session-only states must be based on native `ConfigLayerStack`/loader/runtime evidence, not OpenClaude `allAgents` semantics;
- hot reload: same-thread availability remains explicitly bounded through typed projection state; native `reload_user_config_layer` / `refresh_runtime_config` reload `Config.agent_roles`, the next foreground turn rebuilds `spawn_agent.agent_type` schema from the refreshed role catalog, and the TUI wizard calls existing app-server `reload_user_config` after successful create instead of adding a new role-template endpoint.

OpenClaude markdown/frontmatter remains an import/source-conversion concern, not a runtime profile format. `/agent-roles` links to the same external-agent migration surface as `/import`; app-server `externalAgentConfig/import` then compiles supported `.claude/agents/*.md` fields into native TOML and refreshes runtime config for imported `Subagents`. `tools` maps to `[tool_selection].allowed_tools`, `disallowedTools` maps to `[tool_selection].denied_tools`, and ambiguous external tool names are preserved only as no-grant stale entries or conservative deny aliases. Persistent color, memory prompt injection and role-local profile fields remain excluded until a native Codex contract exists.
