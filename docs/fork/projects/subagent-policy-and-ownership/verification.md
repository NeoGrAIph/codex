## Scenario matrix

- Positive descendant: child `/root/worker` interrupts `/root/worker/child`; `Op::Interrupt` is sent to the descendant and the call succeeds.
- Negative cross-subtree: child `/root/worker` tries to interrupt `/root/sibling`; fail-fast error and no interrupt op is sent.
- Negative root target: existing root target denial remains intact.
- Negative self target: existing self-interrupt denial remains intact.
- Negative pathless MAv2 author: old/pathless non-root `SubAgentSource::ThreadSpawn { agent_path: None }` cannot fall back to root ownership for `spawn_agent`, `send_message`, `followup_task`, `interrupt_agent` or `set_thread_note`; each fails before new child path creation, inter-agent communication, interrupt or metadata mutation.
- Positive close descendant: workbench/app-server close one can close a path-backed spawned descendant and delegates shutdown to native `AgentControl::close_agent`.
- Negative close boundaries: main/root/self/pathless/already-closed/outside-subtree targets are denied before TUI enablement and rechecked server-side by `ThreadManager::close_agent_from_workbench`.
- V1 legacy close parity: path-backed non-root callers can close descendants through `close_agent`, self and sibling targets are denied before shutdown, and root/user callers keep the existing native close path.
- Spawn policy snapshot: V1 and MAv2 spawn paths persist `SubAgentActionPolicySnapshot` in `SubAgentSource::ThreadSpawn`; role-based spawn marks `source = role_applied_config`, default/no-role spawn marks `source = default`.
- Metadata preservation: thread-note and app-server summary metadata updates preserve an existing action-policy snapshot instead of reconstructing `ThreadSpawn` without it.
- Protocol projection: app-server JSON and TypeScript schema fixtures include `SubAgentActionPolicySnapshot`, `SubAgentActionPolicyMode` and `SubAgentActionPolicySource`.
- Role read-only enforcement: role-applied `default_permissions = ":read-only"` resolves the child config to native `PermissionProfile::read_only()` through `apply_role_to_config`, not through `SubAgentActionPolicySnapshot`, and survives the v1/MAv2 spawn handlers' post-role runtime refresh.
- Workbench read-only enforcement: a non-root thread with active native `:read-only` permission profile cannot call workbench mutation entry points (`queue_inter_agent_message`, `send_inter_agent_followup`, `close_agent_from_workbench`, `dismiss_agent_from_workbench`, `retry_agent_from_workbench`, `stop_all_agents_from_workbench`); denial happens in `ThreadManager`, before TUI/app-server success is possible. Root/user orchestration and sandbox-only read-only execution without the active profile keep existing behavior.
- Workbench action allow/deny enforcement: persisted `SubAgentActionPolicySnapshot` on the non-root author controls workbench mutation entry points; absent lists preserve default allow, `allowed_actions` narrows the set and `denied_actions` wins on conflicts.
- Config parser boundary: root-level `[subagent_action_policy]` parses `allowed_actions` and `denied_actions` into `Config.subagent_action_policy`, and duplicate action ids in either list fail fast during config loading.
- Action-policy retention: V1 and MAv2 spawn compile role-applied action policy into `SubAgentSource::ThreadSpawn.action_policy`; enforcement uses that persisted snapshot, not live role files.
- Action-policy management API: `agentRole/actionPolicy/set` writes native user role TOML under `$CODEX_HOME/agents`, replaces or removes `[subagent_action_policy]`, rejects external `config_file` roles, requires experimental API capability and does not mutate existing persisted snapshots.
- Direct MCP execution policy: external `mcpServer/tool/call` requests are checked against the loaded thread's effective `Config.tool_selection` using canonical MCP names before `McpConnectionManager::call_tool` executes; policy denials are client-visible invalid requests, not internal server errors.
- Project role trust gating: trusted project `.codex/agents/*.toml` roles can enter the effective role catalog; untrusted and unknown project layers remain disabled and do not contribute repo-local roles.
- Read-only `.agents` metadata: native filesystem sandbox policy blocks top-level `.agents` writes under workspace-write policy and preserves protected metadata names through legacy/symlink projection paths.

## Known gaps

No dedicated MCP-only allow/deny management verification is required in this package because action-policy enforcement is scoped to workbench actions. Role-level MCP allow/deny is covered by the generic native `tool_selection` contract: role TOML authoring/write APIs, `spec_plan`/`ToolRegistry` enforcement and direct app-server MCP execution checks. Role-level `read_only` is covered through native permission config, spawn runtime-refresh regression tests and ThreadManager workbench mutation denial for non-root authors. Trust gating is covered for project-local role loading through native project layers; user-owned `$CODEX_HOME/agents/*.toml` and explicit user config `config_file` references remain user-config trust, not project trust.
