## Resolved issues

### 2026-06-17 - DeepSeek rejects `developer` role in serialized messages

Status: fixed locally on 2026-06-18.

Observed symptom:

1. Select `deepseek/deepseek-v4-flash` with reasoning `high`.
2. Send an ordinary user turn such as `test`.
3. TUI reports that skills descriptions were shortened to fit the 2% skills context budget, then the request fails with provider/API validation: `messages[1].role: unknown variant developer`, expected `system`, `user`, `assistant`, `tool`, `latest_reminder`.

Evidence and source:

- Current Chat Completions request construction enters `ModelClientSession::build_chat_completions_request` in `codex-rs/core/src/client.rs`.
- `ChatCompletionsApiRequest::new` in `codex-rs/codex-api/src/common.rs` converts base instructions to an initial `system` message; before the fix, `chat_messages_from_response_items` copied `ResponseItem::Message { role, .. }` into `ChatMessage.role` unchanged.
- Codex native context can include `developer` role messages for AGENTS, skills, collaboration modes, model-switch reminders and other developer/context fragments. A DeepSeek-compatible Chat Completions endpoint that rejects `developer` can therefore fail even after provider/model selection succeeds.
- The skills context-budget warning is part of the observed reproduction, but it should be treated as incidental until the captured request body proves it changes the failing role sequence.

Fix and verification:

- `chat_message_role_from_response_role` maps `developer` to `system` only inside the Chat Completions adapter; supported chat roles pass through and unknown roles fail fast.
- Regression coverage: `chat_completions_maps_developer_messages_to_system_role` and `chat_completions_rejects_unknown_message_role`.
- Local check: `just test -p codex-api chat_completions` passed with 8/8 tests, including `latest_reminder` pass-through coverage.
- OpenAI Responses transport remains outside this adapter and continues to use the native Responses request builder.
